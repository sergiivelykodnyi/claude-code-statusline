## Warnings

### WR-01: "Upstream gone" state renders a false green ≡ (claims in-sync)

**File:** `kit/files/home/.claude/statusline.sh:179-188`
**Issue:** `git status --porcelain=v2 --branch` emits `# branch.upstream <ref>`
but **no** `# branch.ab` line when the upstream is configured but its
remote-tracking ref is missing — the "gone" state, which occurs routinely after
a remote branch is deleted and pruned (`git fetch -p` after a PR merge).
`ahead`/`behind` then stay at their `0` defaults, so the new chain falls through
to the `else` branch and prints green `≡` ("in sync: upstream present,
ahead=behind=0"). Verified empirically: a repo with `branch.main.remote`/`.merge`
set but no `origin/main` ref renders `main ≡`. Under the old semantics ≡ merely
meant "has upstream" (config-true); under the new semantics ≡ asserts
"in sync with upstream", which is now a false claim — the branch may be
arbitrarily diverged from the deleted remote. Severity: incorrect display in a
common workflow, no crash or data risk — WARNING.
**Fix:** track whether a `branch.ab` line was actually seen and treat
upstream-without-ab as not-synced (git itself reports this state as "gone"):
```bash
local ... upstream=0 has_ab=0 ...
      '# branch.ab '*) has_ab=1
        ab=${line#'# branch.ab '}
        ...
# in the chain:
    if [ "$upstream" -eq 0 ] || [ "$has_ab" -eq 0 ]; then   # no upstream, or upstream gone
      out="${out} ${RED}≢${RESET}"
```

### WR-02: project-brief.md `ahead`/`behind` entries contradict their own examples and colors

**File:** `project-brief.md:18-19`
**Issue:** The labels are swapped relative to the glyphs, and the new color text
from d0dc9ff makes each line self-contradictory:
- Line 18: "`ahead` - how many commits are ahead in remote, e.g. `↓2` — yellow
  when behind only..." — `↓` is the *behind* glyph, and an entry named "ahead"
  now describes the behind-only color rule.
- Line 19: "`behind` - how many commits are not pushed to remote, e.g. `↑3` —
  blue when ahead only..." — `↑` is the *ahead* glyph.

The swap pre-dates this change, but d0dc9ff edited exactly these two lines and
attached the new color semantics to the wrong labels instead of fixing them.
README.md:24-25 has the correct pairing, so the two spec docs now disagree on
what `ahead`/`behind` mean.
**Fix:** swap the two descriptions so labels, glyphs, and colors agree:
```markdown
- `behind` - commits on the remote not yet pulled, e.g. `↓2` — yellow when behind only, red when also ahead (diverged)
- `ahead` - local commits not yet pushed, e.g. `↑3` — blue when ahead only, red when also behind (diverged)
```
(also swap the order in the Row 1 template on line 8 if glyph order should match
the rendered `↓B ↑A` order).
