## Flagged assumptions (spec-less edge probe — no silent drops)

1. **PORT-01 / PORT-04 sandbox evidence depends on sandboxd** (Docker Desktop) being up — at planning time `sbx daemon status` reported stopped and `sbx ls` could not reach it; Task 2 carries a `<precondition>` and halts for the user rather than faking evidence (prohibition 1).
2. **Engine settings.json rewrite timing (research Open Question 2):** the kit's startup reconcile waits for the platform seed and re-runs on every start; the stop/start probe records whether `.statusLine` is present after restart. If it is absent after the 120 s poll, the CONTEXT fallback (document project-scope `.claude/settings.json`) is applied to the README and recorded — no silent acceptance.
3. **`sbx kit add` scope (research Open Question 1):** the CLI says the container is recreated with the kit appended; the docs list a narrower scope. The probe decides; the README sentence follows the probe.
4. **In-VM latency:** the harness latency budget (10 renders ≤ 2 s) is asserted inside the sandbox too; a FAIL there is a real PORT-02 finding in the sandbox environment and is recorded, not waived.
5. **`sbx exec` user and bind-mount ownership** (research A4): checks use explicit `/home/agent/...` paths and `INSTALLED=` so they do not depend on `$HOME`; files written to `tests/out/sandbox/` from inside the sandbox may carry the sandbox user's ownership — readable on the host, gitignored.

Canon referral (not minted): supply-chain trust of the kit source and the root startup shell are canon security — plan 01 threat register + /gsd-secure-phase.
